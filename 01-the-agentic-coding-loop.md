# Chapter 1 — The Agentic Coding Loop

*Read, reason, act, observe — and why the observe step is the whole game in code*


---

Here is something strange. You can take the same coding agent, the same model, the same repository, the same bug — and get a completely different result depending on one thing that has nothing to do with intelligence.

Let me show you what I mean.

An engineer opens a CLI coding agent and types: *"The `truncate_dialogue` helper drops the last line when the input has no trailing newline. Fix it and make sure the tests pass."* The agent searches for the function, reads it, notices a loop bound that stops one element short, fixes the bound, runs `pytest tests/test_dialogue.py`, and reads back: `3 passed`. Four tool calls. The change is correct.

Now the same agent, the same model, a different repository — one where no test command is configured. Same prompt: *"Fix the bug where the last line gets dropped. Make sure the tests pass."* The agent searches, reads the function, forms a plausible hypothesis, makes an edit — and then writes: *"I've fixed the off-by-one error. The tests should now pass."*

It never ran a test. There was nothing to run. The diff looks reasonable. The prose is confident. And the fix is wrong: the real bug was in a different function the agent never read, and the edit introduced a new off-by-one going the other direction.

The model was identical. The reasoning — the part we usually credit or blame — was nearly identical. What differed was a single edge of a loop. In the first run, the world sent back a real signal after the agent acted. In the second run, there was no signal, so the agent reported on its own work. "The tests should now pass" is not an observation. It is a wish dressed as a result.

That contrast is what this chapter is about. Not intelligence. The loop.

## The loop, named plainly

A coding agent runs four moves in sequence, over and over.

![A four-stage cyclic process. READ at top, REASON at right, ACT at bottom, OBSERVE at left, connected clockwise. The emphasized return edge runs from OBSERVE back to READ, carrying a mechanically generated ground-truth signal. Four signal types sit beside OBSERVE: tests, exit code, diff, stack trace.](../images/01-the-agentic-coding-loop-fig-01.png)
![The read, reason, act, observe loop, with the observe-to-read return edge carrying the ground-truth signal that closes the cycle.](images/01-the-agentic-coding-loop-fig-01.png)
*Figure 1.1 — The read, reason, act, observe loop, with the observe-to-read return edge carrying the ground-truth signal that closes the cycle.*

**Read.** The agent pulls context in. It searches for a symbol, opens a file, reads a function, scans a directory. Everything it knows about your codebase it learned by reading something. At the start of a session it knows nothing about your code — only what the language itself can tell it.

**Reason.** From what it has read, the model plans what to do next. *The relevant bound is here. The test exercises this path. The fix is line 142.* This is the move that looks like thinking, and it is genuinely where the model's capability lives. But it is not the bottleneck. I will come back to that.

**Act.** The agent does something to the world outside its head: edits a file, runs a shell command, invokes a test. Acts are the only step that changes state. An act with no following observation is a change made blind.

**Observe.** The world sends something back.

And here is the thing that makes coding different from almost every other domain where you might deploy an agent: when the observation channel is wired correctly, the signal that comes back is *mechanically generated by tools that do not care what the agent intended.*

A passing test is a passing test. `3 passed` does not negotiate. A type-checker error names the exact line and the exact mismatch. A compiler either accepts the code or it doesn't. A stack trace shows you the frames whether or not the agent predicted them. These are ground truth in a strong sense — they are the world's answer, not the agent's self-assessment.

Then the loop repeats. The observation feeds back into reading and reasoning for the next pass. That feedback arrow is the load-bearing edge of the whole structure. Cut it, and you get run two: read, reason, act, *stop* — and a confident wrong answer.

This structure has a name. Yao and colleagues formalized it as **ReAct** — the model emits a thought, takes an action, ingests the resulting observation, and repeats. It is not a new invention. And coding is not the only place it shows up. But coding is the lucky domain where the observe step can return a signal the agent cannot manufacture for itself. In most of the world, if you ask an agent "did that work?", you have to judge the answer yourself. In code, a test runner judges it for you.

Wiener named the underlying shape in *Cybernetics* in 1948: a goal-directed system needs an actuator, a sensor, a comparator, and a feedback path. The coding agent is a cybernetic feedback loop with a stochastic evaluator in the reasoning seat. Wiener's framing earns its place because it tells you precisely where such systems fail — *where there is no sensor.* An agent with no test command has no sensor on whether its code works. Wiener would have predicted the failure before the engineer typed the prompt.

There is a historical footnote here worth savoring. Around 1963, L. Peter Deutsch implemented the first interactive Lisp on a PDP-1. A programmer could type an expression, have it evaluated, read the result, and type the next one: read, eval, print, loop. A coding agent is that REPL with the model where the human used to sit. The structure is sixty years old. What is new is the stochastic evaluator and the size of what it has to manage — which brings me to the constraint.

## Context is the bottleneck, not intelligence

Say you have a frontier model, and it is smart enough for the task. That is almost always true. The failures do not cluster around "the model cannot reason about this." They cluster around something else: *what the model can attend to at the step where it acts.*

![A line chart with both axes from zero. Tokens consumed rise monotonically with loop iterations toward a fixed capacity ceiling. A degradation-onset line sits at roughly four-fifths of capacity; the band between onset and the ceiling marks where attention quality falls before the hard limit is reached.](../images/01-the-agentic-coding-loop-fig-03.png)
![Context fills monotonically toward a fixed ceiling, and attention quality degrades in a band well before the hard limit.](images/01-the-agentic-coding-loop-fig-03.png)
*Figure 1.3 — Context fills monotonically toward a fixed ceiling, and attention quality degrades in a band well before the hard limit.*

Anthropic's own documentation for Claude Code puts the governing constraint plainly: most of the best-practice guidance exists because the context window fills up fast, and performance degrades as it fills.

Two facts inside that sentence do the work.

**The window is finite, and the loop only ever adds to it.** Every file read, every tool result, every error message, every prior attempt stays in the context window unless you explicitly remove it. A single bug investigation can read a dozen files, run the suite three times, and accumulate several failed-attempt diffs — tens of thousands of tokens. The loop fills the budget by construction. There is no forgetting.

**Quality degrades before the hard limit.** The model does not work perfectly up to the token ceiling and then stop. Attention does not spread evenly over a long window. Early instructions lose salience as later tokens pile in. A window crowded with near-duplicate, superseded, or contradictory material dilutes the signal each token carries. Practitioners have converged on a soft threshold around 80% of capacity as the point where you should compact or restart — not because there is a published curve with error bars behind it, but because the degradation is real and consistent enough that "plan to restart before you fill the last fifth" is better than watching quality erode while you top off the window.

Put these two facts together and the engineering question changes shape. It stops being "how do I make the model smarter." It becomes: *how do I keep what's in the window relevant while still giving the agent the specific lines this task needs?*

There are two levers. Put less in: search to the symbol rather than dumping three 2,000-line files into context to "understand the module." Take stale material out: compact the history, or open a fresh session, when the window fills with sediment that no longer represents the current state of the world.

Here is a concrete failure that makes the cost legible. An agent reads three whole files to understand the module, fills 70% of the window, and then makes a poor edit — not because it cannot reason about the problem, but because the relevant thirty lines are buried among six thousand, and the model's attention has too much to spread across. Same model, same task, clean window: it would have read the thirty lines and fixed it. The bottleneck was never the intelligence. It was what occupied the window at the moment of reasoning.

### A misconception worth killing early

A bigger context window does not dissolve this problem. It raises the ceiling, which buys more iterations before the degradation threshold. It does nothing about the quality of attention over a polluted window. A window full of stale reads and abandoned approaches is a *worse* working context at a million tokens than a clean window at a hundred thousand. Capacity is not signal. The skill is curating what occupies the window, not maximizing the window.

### Two sides of one coin

The chapter's two claims are not separate. "Context is the bottleneck" and "the observe step is the whole game" are the same coin seen from two sides. A clean context is the condition under which the model can reason well — it is the *input* side of the loop. A real observation channel is the condition under which the model can know whether it reasoned correctly — it is the *output* side. Starve either and the loop fails: a polluted window degrades the reasoning; a missing test command leaves even good reasoning unverified.

The engineering discipline the rest of this book teaches reduces to one line: *feed the loop clean context and close it against ground truth.* Everything from Chapter 2 onward is a specialization of that sentence.

## An open loop is an agent guessing — the diagnostic

When an agent confidently does something wrong in code, the most useful question is not "why didn't the model get it right?" It is: *did the observe edge close, or was the agent self-reporting?*

That question routes you to the right fix faster than any other.

Four beliefs are worth retiring because each one is an open-loop trap in disguise.

*"The skill is prompting the model well."* It is not. The skill is designing the loop — what context goes in, and what ground-truth signal comes back out. A perfectly worded prompt over an open loop still produces run two from the opening example.

*"More context is better."* No. Context fills fast and degrades; relevance beats volume. Dumping the repository into the window is the architectural version of this mistake.

*"The agent knows whether it succeeded."* No. Without a real observation channel, the agent is self-reporting, and self-reports from a language model are unreliable in a specific, dangerous direction: they skew confident and agreeable. "The tests should now pass" is the signature of an open loop.

*"It's one-shot, like chat."* No. It is a stateful, accumulating loop. What the agent read and tried three turns ago still occupies the window and still shapes its reasoning now. Treating it as one-shot is what makes context rot invisible until it bites.

Here is the diagnostic in operational form.

**Was there a ground-truth channel at all?** If the agent never ran a test, never invoked the type-checker, never re-read its own diff — the loop was open. It could not have known. The fix is to wire the channel: give it the exact test, typecheck, lint, or build commands so the next act produces a real observation. This is the most common failure in a fresh setup, and the cheapest to fix.

**Was there a channel, but the agent didn't use it?** If a test command exists but the agent cited a command the project does not use, or declared success without running it — the channel is present but not enforced. The fix is to make running it part of the loop's stopping condition.

**Did the channel return a true signal that the agent then ignored or misread?** This is rarer and more interesting. The test failed. The agent saw the failure. And it reasoned past it — often because the window is so full of prior attempts that the fresh failure has to compete with sediment for attention. That is a context failure. The fix is a clean window, not a better prompt.

The empirical backbone for "the observation channel is part of the system design, not cosmetic" comes from Yang and colleagues' SWE-agent work. They framed a language-model agent as a new category of end user that interacts with a codebase through a deliberately designed agent-computer interface: read a file, search the repo, edit, run tests, observe output. Their central result is that the interface — not just the model — determines success. Holding the model fixed and changing only the interface, adding edit-time linting, constraining how files are viewed, scoping search, materially changed the rate at which the agent resolved real GitHub issues on SWE-bench. That is the academic proof that wiring the read and observe edges well is the engineering, and that the work happens *around* the model, not inside it.

One honest caveat. There is a live debate about how much the scaffold versus the model matters going forward. SWE-agent argues the interface is decisive; others argue that as frontier models absorb more scaffolding through agentic post-training, the model increasingly does internally what the interface used to do for it. This book sides with "the loop you build still matters" — because even a model that explores well cannot verify against a channel you never gave it. A test that is never run still tells you nothing.

## LLM Exercises

**Exercise 1.1 — Understand → Analyze.** Take a recent real run where your agent did something confidently wrong in a codebase. Reconstruct it as a loop trace: label each step you can identify as READ, REASON, ACT, or OBSERVE. Then mark the observe edges — for each ACT, write down what signal (if any) came back, and whether it was mechanical ground truth (a test result, a compiler error, a re-read diff) or the agent's self-report. Identify the first edge that broke. State, in one sentence, whether the failure was an open observe channel, an unused channel, or a true signal ignored — and why.

**Exercise 1.2 — Analyze, contrast.** Run the same small task twice on a repository you control. Run A: give the agent the exact test command and the instruction "don't stop until the tests pass; run them and show me the output." Run B: remove the test command from the conversation and say "fix it and make sure it works." Capture both transcripts. Write a short comparison: in which run did the loop close against ground truth, and what specifically did the agent substitute for an observation in the run that failed to close? If both runs happen to produce correct code, increase the task's difficulty until the open-loop run guesses wrong — the contrast is the lesson.

**Exercise 1.3 — Apply, produce something.** Pick one coding task you do often: fix-a-failing-test, trace-a-stack-trace-to-a-fix, mechanical rename. Write a one-page loop spec for it that a teammate could follow. Name the READ the agent should do first (which symbol to search for, which file to open — not "read the module"). Name the ACT. Give the exact OBSERVE command that closes the loop for this task type — the literal test, typecheck, or build string, with the failing assertion or error output as the signal. Add one line on context-budget discipline: what the agent should *not* read, to keep the relevant lines from drowning. You will reuse this in Chapter 2 when you wire it into a real `CLAUDE.md`.

## What would change my mind

The chapter's load-bearing claim is that in coding agents the limiting factor is the loop's edges — context in, ground-truth signal out — far more than the model's raw reasoning. A controlled study that held the loop fixed and varied only model capability, and found that model capability dominated outcome variance across a representative set of real coding tasks, would force me to weaken "context is the bottleneck, not intelligence." The honest form of the claim is conditional: *given a competent frontier model*, the marginal returns are on the loop. If a generation of models arrives for which that condition no longer holds, the emphasis would have to move.

Separately, if SWE-agent-style interface ablations stopped mattering — if a frontier model resolved real issues at the same rate whether or not you gave it a well-shaped observation channel — that would not refute "the loop matters," but it would refute "the engineer must author the loop." I would watch the SWE-agent ablation result over successive model generations as the bellwether.

## Still puzzling

**Is "context rot" one phenomenon or several?** The chapter lumps stale reads, superseded approaches, and contradictory corrections under "the window degrades as it fills," because they share a fix — a clean window. It is not obvious they share a mechanism at the attention level. Position effects, near-duplicate dilution, and contradiction-handling might be three distinct failures wearing one name. The operational advice survives; the mechanism story is unsettled.

**Where exactly is the degradation threshold, and is it a cliff or a slope?** The 80% heuristic is practitioner lore, not a measured curve with error bars, and it surely varies by model and task. A published degradation curve would turn a rule of thumb into something an engineer could budget against — and might reveal that "restart at 80%" is too conservative for some models and too lax for others.

**As models internalize scaffolding, does the "interface is decisive" result weaken?** If agentic post-training keeps absorbing what the interface used to do, the authoring of the read and observe edges may migrate from the engineer to the model. The existence of a ground-truth channel cannot become optional — a test never run signals nothing — but *who builds the loop* might change. Which trend wins is genuinely open; this book bets on "you still author the verification," and flags the bet as a bet.

**Does a stochastic evaluator in Wiener's comparator seat behave like the deterministic comparators cybernetics studied?** The loop is a feedback system, but the element deciding "have we reached the goal?" is a sampling language model, not a fixed function. Whether classical control-theory intuitions about stability, oscillation, and overcorrection transfer to a loop whose comparator is stochastic is a question this chapter raises and does not resolve.
