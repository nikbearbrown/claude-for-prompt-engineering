# Chapter 5 — Refactoring and Large-Scale Code Transformation

*Driving a mechanical multi-file change with scope discipline and a behavior-preservation oracle*

---

Most coding tasks make you invent the success condition. "Add a feature" — define done. "Improve performance" — define how much, measured how. Refactoring is different, and the difference is the whole reason it is the cleanest task in this book.

Here is Martin Fowler's definition, from *Refactoring* (2nd ed., 2018): a refactoring is "a change made to the internal structure of the code that doesn't modify its observable behavior," achieved "through a series of small behavior-preserving transformations." The boundary line, stated flatly: "if you change the behavior… you are not refactoring."

Read that as an engineer reading a spec. The success condition is already written: observable behavior unchanged. You do not have to invent the oracle — the task definition hands it to you before you start. For a refactor, the loop is fully specified up front. The engineering question collapses to a single one: **what is my behavior-preservation check, and is it strong enough?**

The lineage goes back further than Fowler. William Opdyke coined the term in his 1992 dissertation and his framing is sharper: refactorings are behavior-preserving *provided that their preconditions are met*. Each transform — rename this method, extract that function — is safe only when a set of guards holds: the new name doesn't collide, the extracted code has no hidden dependency on local state you're about to sever. A transform is not "safe" in the abstract; it is safe *when its preconditions hold*, and your job is to check them. This is exactly the mental model an agentic codemod needs.

That is the good news. Now the bad news.

---

## The shock: good and unsafe at the same time

Before trusting an agent with a refactor, you should know its actual track record. Liu et al. (2024) evaluated LLM refactorings against 180 real-world refactorings performed by human experts.

![A horizontal bar chart on a shared zero-origin axis. The comparable-or-better fraction is a long bar at about sixty-four percent. The unsafe fraction is a short bar at about seven percent. The model cannot tell which bucket a given refactor falls into.](../images/05-refactoring-and-code-transformation-fig-04.png)
![LLM refactors split into a large comparable-or-better fraction and a small unsafe one the model cannot identify.](images/05-refactoring-and-code-transformation-fig-04.png)
*Figure 5.1 — LLM refactors split into a large comparable-or-better fraction and a small unsafe one the model cannot identify.*

Two findings, and you need both at once.

The promising one: roughly **63.6%** of ChatGPT's refactoring solutions were comparable to or better than the human-expert refactoring. That is genuinely strong. An agent that matches or beats an expert on nearly two-thirds of refactorings is a real tool, not a toy.

The dangerous one: **13 of 176** ChatGPT solutions and **9 of 137** Gemini solutions were *unsafe* — they changed functionality or introduced syntax errors. That is on the order of 7%. And the paper names the mechanism precisely: generic LLMs "do not validate the equivalence of input and output code." The model proposed each refactoring with the same confident tone whether it preserved behavior or silently broke it. It had no internal sense of which.

Hold those two numbers together, because together they *are* the chapter's argument. Good 64% of the time. Unsafe 7% of the time. And — this is the load-bearing part — **it cannot tell you which bucket a given refactor is in.** A refactor that subtly changes a boundary condition reads, in the diff, exactly like one that doesn't. The prose explanation is equally fluent for both. There is no tell.

This is why "ask the agent to refactor and read the diff" is not a method. Reading the diff catches syntax errors and obvious behavior changes. It does not reliably catch the subtle boundary-condition flip, which is precisely the unsafe class that matters. The 7% does not announce itself.

The conclusion is forced: **an LLM refactor without a behavior-preservation check is not a refactor.** It is a behavior change with a 7%-ish probability you didn't intend, dressed in refactoring language.

One misconception deserves to be killed explicitly: "the agent explained why the refactor is safe, so it's safe." The explanation and the safety are *uncorrelated* in the unsafe cases — that is the whole content of "does not validate equivalence." The explanation is generated by the same process that generated the unsafe edit; it is not an independent check. An external oracle is independent. The model's prose is not.

## Two lanes: deterministic codemod vs. freehand edit

Not all refactors should be done the same way, and the most important decision you make is *which lane a refactor belongs in* before the agent touches anything.

![A flowchart. An incoming refactor task meets one decision: does the transform generalize uniformly across many sites. Yes routes to the deterministic codemod lane, choose-and-run then verify. No routes to the freehand agentic-edit lane, edit under scope discipline then oracle guard. Both lanes reconverge at a verified result.](../images/05-refactoring-and-code-transformation-fig-01.png)
![One question routes a refactor into the deterministic-codemod lane or the freehand-agentic-edit lane, reconverging at verification.](images/05-refactoring-and-code-transformation-fig-01.png)
*Figure 5.2 — One question routes a refactor into the deterministic-codemod lane or the freehand-agentic-edit lane, reconverging at verification.*

**Lane one: the deterministic codemod.** When a transform generalizes across many call sites — rename a widely-used method, replace a deprecated API everywhere, change a function's argument order across a service — the right tool is usually not freehand editing. It is a program that transforms the program. Parse the source to an abstract syntax tree, transform the AST, reprint.

This is the lineage of `jscodeshift`, the toolkit Meta built to update APIs across a JavaScript/TypeScript codebase with thousands of files where manual edits were error-prone. The original production motivation was sweeping React API renames across a huge codebase — deterministically, in one pass. The transform is a function: same input, same output, every time. It does not get tired on file 4,000 and introduce a typo. It either applies or it doesn't, and where it doesn't, it tells you.

The stronger modern example is OpenRewrite, which raises the ceiling further. OpenRewrite operates on a *Lossless Semantic Tree* (LST): an AST enriched with full type information and preserved whitespace. Because it carries types, its transforms are type-aware — it knows that *this* `save()` is the one on your repository class, not a different `save()` elsewhere. Its "recipes" are deterministic LST programs — rename a method, upgrade Spring Boot 2 to 3 — runnable across thousands of repositories. A Spring Boot migration recipe is a real, complex, multi-step behavior-preserving transformation that someone already wrote and tested.

For a mechanical, generalizing transform, a deterministic tool gives you determinism *plus* scale. The unsafe-edit rate of the Liu et al. study is largely a freehand-LLM problem, not a codemod problem.

**Lane two: the freehand agentic edit.** When the transform does *not* generalize — the change is shaped differently at each site, requires judgment about local context, or is one-off — a deterministic codemod costs more to write than it saves. Here the agent's flexibility is the point. Extract this specific tangle of a function into well-named helpers; restructure this one module's control flow. You let the agent edit, and you lean hard on scope discipline and the oracle.

**The decision rule:**

> Does the transform generalize across many sites in a uniform way?
> **Yes →** deterministic codemod lane. The agent's job is to *choose and run* the transform, triage residual failures, and verify behavior — not to hand-edit thousands of sites.
> **No →** freehand agentic-edit lane. The agent edits directly, under tight scope discipline, with the oracle as the guard.

Note the agent is useful in *both* lanes. In the codemod lane it writes and validates the transform — a higher-leverage act than typing the edits. The frontier model's best contribution to a 4,000-file rename is the 40-line codemod, not 4,000 edits.

## Scope discipline: small steps and a blast-radius budget

Now the freehand lane, where the danger is highest. The discipline is Fowler's: **a series of small behavior-preserving transformations**, running the tests between each, so the system never stays red for long.

![A cycle. One small transform feeds a stay-green gate. On pass, the change commits and proceeds; on fail, the single step is reverted. Both the commit and the revert path return to the small-transform node, closing the loop for the next step.](../images/05-refactoring-and-code-transformation-fig-02.png)
![Each refactor step is one small transform behind a stay-green gate that either commits and proceeds or reverts and retries.](images/05-refactoring-and-code-transformation-fig-02.png)
*Figure 5.3 — Each refactor step is one small transform behind a stay-green gate that either commits and proceeds or reverts and retries.*

Why small steps? Because the size of a step is the size of the thing that can go wrong. If you ask the agent to "extract these five helpers and inline that abstraction and rename the module" in one diff, and the suite goes red, you have a large, entangled diff to debug and no idea which sub-change broke it. If instead each step is *one* extraction — run the suite, commit if green — then a red suite localizes the fault to the single step you just took. You revert one step, not an hour of work. Small steps turn debugging-the-refactor into a binary search with a step size of one.

Three mechanical parts you give the agent explicitly:

**Small steps.** One transform per step. Extract *one* function, not five. Rename *one* symbol, then run the check.

**A stay-green gate between every step.** After each step, run the behavior-preservation oracle. Green → commit, proceed. Red → **revert this step** and try again differently. The gate is non-negotiable; it is the only thing standing between you and the 7%.

**A blast-radius budget.** Cap what a single refactor is allowed to touch: files-touched and diff-size limits, an explicit "only `src/render/`; ask before editing anything else" scope. When the agent wants to exceed the budget, that is a signal — either the refactor is bigger than you scoped, or the agent has lost the thread.

Watch what happens without the gate. A too-big agentic refactor that goes red early keeps editing *on top of* the broken state — now it is changing behavior to chase a failing test, layering edits onto a base that was already wrong, and the diff grows past the point where any human can review it. The "stay green between steps" gate prevents that spiral: you never build the next step on an unverified base. Each green checkpoint is a place you can stand.

## The oracle: how strong is your behavior-preservation check?

When the agent says "behavior preserved," how do you *know*? This is where the chapter's thesis bites, because the oracle's strength is the refactor's safety. A weak oracle is a 7% gamble with extra steps.

There is a ladder of oracles, weakest to strongest, and you should know where yours sits.

![A four-rung ascending staircase of behavior-preservation oracles, increasing in strength: the existing test suite, characterization tests pinning risky behavior, the deterministic codemod's own guarantee, and equivalence checking or differential fuzzing. A vertical arrow marks increasing strength.](../images/05-refactoring-and-code-transformation-fig-03.png)
![Behavior-preservation oracles form a four-rung ladder of increasing strength, from the existing suite to direct equivalence checking.](images/05-refactoring-and-code-transformation-fig-03.png)
*Figure 5.4 — Behavior-preservation oracles form a four-rung ladder of increasing strength, from the existing suite to direct equivalence checking.*

**Rung one: the existing test suite.** This is the Chapter 4 PASS_TO_PASS guard, repurposed. Before the refactor, the suite is green. After each step, it must stay green. A refactor that turns a previously-passing test red has, by definition, changed observable behavior — caught. This is necessary, it is cheap, and you should always have it. But it is **coverage-limited**: the suite only checks the behaviors it tests. A boundary condition no test exercises can flip and the suite stays green. The Liu et al. unsafe edits that "changed functionality" are exactly the ones a thin suite misses. The existing suite is the floor, not the ceiling.

**Rung two: tests written to pin the behavior you're about to refactor.** Before touching a function, add characterization tests that capture its current behavior — including the edge cases you suspect the agent might mangle. This is reproduce-first discipline applied to refactoring: you don't trust the suite to cover the risky region; you *make* it cover the risky region before you let the agent edit. Cheap insurance against the specific unsafe class.

**Rung three: a deterministic codemod's own guarantee.** If you're in the codemod lane, the transform's determinism is part of the oracle. An OpenRewrite recipe operating on a type-aware LST is behavior-preserving by construction for the transforms it implements. You still run the tests, but the surface of possible error is far smaller than freehand editing. This is a real reason to prefer the codemod lane where it applies: it doesn't just scale, it *narrows the oracle's job*.

**Rung four: equivalence checking.** The frontier of the field is checking directly whether two program versions are semantically equivalent — independent of any test suite you happened to write. EquiBench (arXiv:2502.12466) is the established reference: a benchmark for program equivalence checking. Differential fuzzing pushes on the same goal from another direction — run thousands of generated inputs through both versions and compare outputs, surfacing a divergence the fixed suite never thought to test.

In practice this rung is immature and language-limited: EquiBench shows that even the best model reaches only around 82% overall accuracy and barely beats a coin-flip on its hardest equivalence categories. Treat the whole rung as emerging, not production-ready. But it is the direction the oracle is heading, and it is worth knowing that "passing tests" is not the end of the ladder.

The practical posture: **start at rung one always, climb to rung two for any risky refactor, prefer rung three where the transform generalizes, and reach for rung four when the stakes justify it.** An agent's refactor is only as good as the rung you stand on. The 7% lives in the gap between your oracle's coverage and the behavior's true surface. Climbing the ladder shrinks that gap.

A second misconception to kill: "Green tests prove behavior is preserved." No — green tests prove the *tested* behavior is preserved. The unsafe refactor that flips an untested boundary condition passes a green suite. This is why rungs two and four exist. A passing suite is necessary, not sufficient.

## A worked scoped-refactor workflow

Put it together as the workflow you'd actually drive.

*The task.* A text-adventure engine has the dialogue-truncation logic duplicated across two call sites in `src/render/`. Extract the logic into a single helper both sites call. Mechanical, bounded — Chapter 3's strong quadrant.

*Step 0 — define the oracle first.* Before any edit, write characterization tests pinning the *current* truncation behavior at both sites, explicitly including the empty-dialogue and single-line edge cases. Run the suite: green. Now the risky region is covered, not assumed. The check exists before the change.

*Step 1 — pick the lane.* Does the transform generalize across many sites? No — two sites, shaped slightly differently, judgment about which behavior is canonical. Freehand lane. A codemod would cost more than it saves.

*Step 2 — small step, with the gate.* The agent extracts the helper and rewrites the *first* call site to use it. Run the suite. Green → commit. Had it gone red, revert this one step and retry — the fault is localized to a single call-site rewrite, trivial to debug.

*Step 3 — second small step, gate again.* Rewrite the *second* call site to use the helper. Run the suite. Green → commit. Two steps, two green checkpoints, two cheap-to-revert units.

*Step 4 — scope guard.* Diff touches three files (the two call sites and the helper's new home), well within budget; nothing outside `src/render/` changed. Pass.

*Step 5 — behavior-preservation verdict.* Suite green, including the edge-case characterization tests written in step 0. For a higher-stakes version of this refactor, add a differential-fuzzing pass (rung four) over the old and new truncation functions; here the pinned edge cases plus the full suite are a defensible bar. Ship.

What made this safe was not the agent's skill. It was the oracle written before the edit, the small steps with a gate between them, and the scope budget — the disciplines, not the model.

Contrast with the unsafe version: "Agent, deduplicate the truncation logic in `src/render/`." One big diff, no characterization tests, read-the-diff-and-trust. If the agent's extraction quietly changed how the empty-dialogue case truncates — the Liu et al. unsafe class — the green suite wouldn't catch it (no test for empty dialogue), the diff would look plausible, and you'd ship a behavior change calling it a refactor. Same agent. Different outcome. The difference is the workflow.

## Bridge to debugging

Refactoring gave us the cleanest version of the thesis because the oracle came pre-specified: behavior preservation, written into the task definition. You build the check, drive small steps against it, and reject anything that fails.

Debugging is the same machinery aimed at the opposite target. In refactoring you hold behavior *fixed* and change structure. In debugging you hold structure roughly fixed and *change behavior* — from wrong to right — and the oracle is a failing test you must first make pass. The reproduce→localize→fix→verify loop of Chapter 6 is the refactor loop run in reverse: instead of "stay green," you start red and earn green. And the failure mode rhymes exactly with this chapter's 7%: an agent that "fixes" a bug confidently, turns the one test green, and is *wrong* — the confident-wrong-fix, debugging's version of the unsafe refactor. The cure is the same shape: external grounding the model can't fake.

## What would change my mind

A controlled study showing that frontier coding agents reliably self-detect their own behavior-changing refactors — flagging the unsafe 7% from the inside, without an external oracle, at a rate high enough to trust — would undercut this chapter's core move. The whole argument rests on Liu et al.'s mechanism: the model "does not validate the equivalence of input and output code," so the explanation and the safety are uncorrelated in the unsafe cases. If a later model closed that gap internally — produced a calibrated "I am not sure this preserves behavior" exactly when it doesn't — then the external oracle would become a backstop rather than the main event. I would want to see that on a held-out set of real refactorings with a strong equivalence oracle as ground truth, not on the model's self-report. I am not expecting it soon, but it is the falsifiable form of the claim.

## Still puzzling

**Where exactly does the agent-vs-codemod boundary sit, and does it move with model capability?** The rule "deterministic where it generalizes" is sound in shape but the threshold — at what scale freehand editing beats writing a transform — is lore, not data. As agents get better at freehand multi-file edits, the crossover scale should rise; as they get better at *writing* codemods, the codemod lane should widen. Which effect dominates is unmeasured.

**What is an adequate behavior-preservation oracle, practically?** A passing suite is coverage-limited; equivalence checking and differential fuzzing are stronger but immature and language-limited. There is no consensus bar for "preserved enough to ship." The ladder is a posture, not a measured standard.

**Can we automatically flag which LLM refactors changed behavior, without a strong oracle?** Liu et al. show ~7% unsafe; nobody has a reliable cheap detector that says "this specific diff is the unsafe one" short of running a real equivalence check. If such a flag existed, it would change the workflow from "check everything" to "check the flagged ones."

**Do scope-discipline metrics actually predict success?** Small steps and a bounded diff plausibly make agentic refactors safer, and the intuition matches the debugging story. But the specific bounds that predict agent success on multi-file transforms have not been measured. The thresholds are conservative defaults, not validated knobs.
